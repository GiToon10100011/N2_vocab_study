# 실전 테스트에 뜻 입력 더하기

상태: 구현 중 · 운영 반영 전 (2026-10-30)
앞선 설계: `2026-10-22-typing-test-design.md` (읽기 타이핑)

## 왜

실전 테스트는 한자를 보고 읽기만 쳤다. 읽기는 알지만 뜻은 모르는 단어를 잡아내지 못한다. 뜻도 직접 쳐서 답하게 한다.

## 사용자가 정한 것

- 뜻도 입력한다. (2026-10-30 「뜻 입력하는것도 있어야합니다」)
- **뜻이 비슷하면 부분 점수.**
- **뜻에 괄호가 있으면 괄호 안 내용을 포함하지 않아도 맞는 것으로 한다.**
- **뜻이 쉼표로 여러 개 붙어 있으면 목록 중 하나만 맞혀도 맞는 것으로 한다.**
- **한 단어에 읽기와 뜻을 둘 다 묻는다.** 읽기를 제출하면 읽기 결과만 나오고 뜻은 나오지 않는다.
- **부분 점수는 맞힌 것으로 쳐서 단어 주기를 내리지 않는다.**

## 흐름

```
읽기 입력 ─제출→ 읽기 결과(정답 읽기 · 대조. 뜻은 DOM 에도 없다) ─Enter→
뜻 입력   ─제출→ 뜻 결과(맞음 / 부분 정답 0.5 / 틀림, 정답 뜻) ─Enter→ 다음 단어
```

- 답은 뜻까지 낸 뒤에 한 문항으로 보관한다(`typed` + `typedMeaning`). 읽기만 내고 나가면 그 문항은 안 푼 채로 남아 처음부터 다시 나온다.
- 입력칸 하나를 단계에 따라 「읽기」 → 「뜻」 으로 바꿔 쓴다. 포커스를 잃지 않아 아이폰 키보드가 내려가지 않는다.
- 판정 줄은 단계마다 두 줄 자리다(기존과 같다). 한자와 입력칸은 어느 단계에서도 움직이지 않는다.

## 뜻 판정 (`lib/meaning-answer.ts`)

정답 뜻 → 받아들이는 꼴:

1. 괄호 밖의 `, ， 、 ; ； / ／` 로 나눈다(괄호 안의 쉼표는 나누지 않는다). 항목 하나라도 맞으면 정답.
2. 항목마다 「괄호 안을 뺀 꼴」과 「괄호 안을 푼 꼴」 둘이다. 부분 점수의 기준은 뺀 꼴뿐이다 — 괄호 안 보충 설명만 적어 점수를 받지 못하게.
3. 공백과 문장부호는 무시한다.

입력 한 조각 t 와 정답 꼴 e:

| 조건 | 점수 |
|---|---|
| 같다 | 1 |
| 용언 어미(-하다 · -되다 · -이다 · -다)를 뗀 어근이 같고 어근이 2자 이상 | 1 |
| 어근이 같은데 1자 | 0.5 |
| 한쪽 어근이 다른 쪽에 들어 있고 짧은 쪽이 긴 쪽의 절반 이상 (2자 이상) | 0.5 |
| 어근 자모 이중음 Dice ≥ 0.8 (받침 하나 차이 정도) | 0.5 |
| 그 밖 | 0 |

입력에도 쉼표로 여러 조각을 쓸 수 있고, 앞의 세 조각 중 가장 높은 점수를 받는다(줄줄이 적어 하나가 걸리게 하는 것을 막는다).

**한계 — 철자만 본다.** 뜻이 같은 다른 낱말(동의어)은 알아보지 못한다. AI 를 쓰지 않는다는 절대 규칙 8 때문이다. 그런 답은 정답 목록에 그 낱말이 있어야 맞는다.

기준값은 단어장(`backups/words.csv`, 한자 단어 369개)의 뜻끼리 견줘 정했다. 처음에는 전체 철자의 Dice ≥ 0.7 이었는데 서로 다른 단어 156쌍이 부분 점수를 받았고 대부분 어미 「-하다」가 겹친 우연이었다(해당하다 ~ 당황하다). 어근만 견주고 「포함」 조건을 더하고 Dice 기준을 0.8 로 올려 철자가 가까운 서로 다른 단어 쌍을 23개(어미만 다른 쌍 포함)로 줄였다.

## 채점 (SRS)

단어 하나가 한 번의 채점이다(`planTestGrades`).

- 맞힘 = 읽기 정답 **그리고** 뜻 점수 ≥ 0.5. 주기는 그대로(테스트 정답은 stage 를 올리지 않는다), 카운터는 한 번만 올린다.
- 틀림 = 둘 중 하나라도 아님. stage 1 · 내일. 오답 카운터는 한 번만 올린다.
- 약점 유형: 읽기를 틀렸으면 `s2r`, 뜻만 틀렸으면 `s2m` → 다음 플래시카드가 뜻을 묻는다.
- 로그: 읽기 `s2r` 한 줄 + 뜻 `s2m` 한 줄, 둘 다 `test = true`. 유형 enum 은 늘리지 않는다 — 한자 → 뜻 타이핑은 기존 `s2m` 이다.
- 「읽기 주의」 배지는 읽기 이력만 본다. 재시험 · 통과 선택과 같은 날 카드 채점 가드는 뜻 실패도 틀린 것으로 센다.

## 데이터

`typing_test_items` 에 두 열을 더한다. 읽기만 묻던 때의 답은 두 열이 null 이다.

- `typed_meaning text` — 친 뜻 (공개 백업에 넣지 않는다)
- `meaning_credit real` — 1 / 0.5 / 0

`correct` 는 읽기만 뜻한다. 서버는 클라이언트가 보낸 점수를 받지 않고 친 뜻으로 다시 채점한다.

## 호환 · 배포 순서

- 뜻 답이 없는 요청(배포 전 열려 있던 옛 화면)은 읽기만 반영한다. 영수증 열쇠 입력도 예전 그대로다.
- 열이 없는 DB 에 코드가 먼저 올라가도 화면은 죽지 않는다(`to_jsonb` 로 읽는다). 다만 뜻이 담긴 답은 503 으로 거절된다(클라이언트가 지우지 않게). **그래서 운영 DB 에 스키마를 먼저 올린 뒤 코드를 배포한다.**

## 내가 정한 것 (바꿀 수 있다)

- 부분 점수 기준(포함 · Dice 0.8). 처음 본 적용이라 실제로 써 보고 조정한다.
- 입력 조각은 앞의 세 개만 본다.
- 어근이 같으면 정답(유쾌 ↔ 유쾌하다). 어근이 한 글자면 부분 점수.
- 끝 화면: 「N문제 중 M개」(M = 맞힌 것으로 친 단어 수) 아래에 「읽기 a / N · 뜻 b / N」(b 에 0.5 점 반영). 부분 정답 단어는 따로 나열한다.
- 읽기 결과 뒤 뜻 입력으로 넘어가는 데 Enter 를 한 번 더 누른다(결과를 읽을 자리).

## 알려진 비용 — 실기기 미확인

- 읽기는 일본어(플릭) 또는 영문(로마자) 키보드로, 뜻은 한글 키보드로 쳐야 한다. 단어마다 키보드를 바꾸는 부담이 크면 「읽기 전부 → 뜻 전부」 두 묶음으로 바꾸는 길이 있다(키보드 전환이 한 번).
- 한 단어에 Enter 가 최대 6번이다(확정 · 제출 · 뜻으로, 확정 · 제출 · 다음).
- 시간이 대략 2배가 된다. 문제 수는 설정(10~100)에서 줄일 수 있다.
